# DayBrief AI — Long-term Memory 구조 설계

## 1. 설계 목적

사용자의 관심사와 뉴스 피드백을 장기적으로 관리하여, 시간이 지날수록 개인의 선호에 적합한 뉴스 브리핑을 제공하는 것을 목표로 한다.

장기 기억은 단순히 과거 대화를 저장하는 것이 아니라, 사용자에게서 얻은 정보를 구조화하고 뉴스 선별 및 요약에 활용할 수 있도록 설계한다.

본 문서는 데이터 구조와 처리 원칙을 정의하며, 실제 데이터베이스 구축 및 서비스 연동은 포함하지 않는다.

## 2. 핵심 설계 원칙

- 사용자별로 기억을 분리한다.
- 현재 선호 상태와 과거 피드백 기록을 구분한다.
- 일회성 피드백만으로 사용자 선호를 크게 변경하지 않는다.
- 사용자의 관심사가 바뀌면 기존 선호를 수정하고 변경 이력을 남긴다.
- 근거가 부족한 선호는 확정된 사실처럼 저장하지 않는다.
- 서비스 제공에 필요한 정보만 저장하고, 불필요한 개인정보는 수집하지 않는다.

## 3. 데이터 구조

### 3.1 User Preferences — 현재 사용자 선호

사용자의 현재 관심사와 브리핑 선호를 저장한다.

| 필드 | 자료형 예시 | 설명 |
|---|---|---|
| user_id | string | 사용자 식별자 |
| keywords | list | 관심 키워드 목록 |
| topic_preferences | list | 주제별 선호도 |
| briefing_preferences | object | 브리핑 형식 관련 선호 |
| updated_at | datetime | 마지막 갱신 시각 |

예시:

```json
{
  "user_id": "user-001",
  "keywords": ["AI", "스타트업", "개발자 이직"],
  "topic_preferences": [
    {
      "topic": "AI",
      "preference_score": 0.8
    },
    {
      "topic": "스타트업",
      "preference_score": 0.6
    }
  ],
  "briefing_preferences": {
    "summary_length": "short"
  },
  "updated_at": "2026-10-15T09:00:00+09:00"
}
```

선호도 점수의 범위는 0~1로 정의할 수 있다. 점수가 높을수록 선호도가 높다는 의미이며, 초기에는 명시적으로 등록한 관심사와 피드백을 구분하여 관리한다.

### 3.2 Feedback History — 뉴스 피드백 기록

사용자가 특정 뉴스나 브리핑에 대해 남긴 피드백을 기록한다.

| 필드 | 자료형 예시 | 설명 |
|---|---|---|
| feedback_id | string | 피드백 식별자 |
| user_id | string | 사용자 식별자 |
| news_id | string | 대상 뉴스 식별자 |
| feedback_type | string | 피드백 유형 |
| created_at | datetime | 피드백 발생 시각 |

피드백 유형 예시:
- useful: 유용한 뉴스
- not_relevant: 관심과 관련성이 낮은 뉴스
- too_similar: 비슷한 뉴스가 반복됨
- more_like_this: 비슷한 주제의 뉴스 선호

예시:

```json
{
  "feedback_id": "feedback-001",
  "user_id": "user-001",
  "news_id": "news-001",
  "feedback_type": "useful",
  "created_at": "2026-10-15T09:30:00+09:00"
}
```

피드백 기록은 원본에 가깝게 보존하며, 기존 기록을 덮어쓰기보다 새로운 기록을 추가하는 방식을 기본으로 한다.

### 3.3 Preference History — 관심사 변경 이력

현재 선호도가 어떤 근거로 변경되었는지 추적한다.

| 필드 | 자료형 예시 | 설명 |
|---|---|---|
| history_id | string | 변경 이력 식별자 |
| user_id | string | 사용자 식별자 |
| topic | string | 변경 대상 주제 |
| previous_score | number | 변경 전 선호도 |
| new_score | number | 변경 후 선호도 |
| reason | string | 변경 근거 |
| changed_at | datetime | 변경 시각 |

이 구조를 통해 사용자의 관심사가 시간에 따라 어떻게 변했는지 확인할 수 있다.

### 3.4 Memory Summary — 요약된 장기 기억

반복적인 피드백을 분석해 뉴스 선별에 직접 활용할 수 있는 선호 정보를 정리한다.

| 필드 | 자료형 예시 | 설명 |
|---|---|---|
| user_id | string | 사용자 식별자 |
| memory_summary | string | 요약된 선호 정보 |
| evidence_count | integer | 참고한 피드백 수 |
| updated_at | datetime | 마지막 갱신 시각 |

예시:

```json
{
  "user_id": "user-001",
  "memory_summary": "AI 개발 도구 및 개발자 채용 관련 뉴스에 관심이 높음.",
  "evidence_count": 5,
  "updated_at": "2026-10-15T10:00:00+09:00"
}
```

요약된 기억은 원본 피드백을 대체하지 않는다. 원본 기록을 근거로 다시 생성할 수 있는 파생 정보로 취급한다.

## 4. 장기 기억 갱신 흐름

1. 사용자가 관심 키워드를 등록하거나 뉴스에 피드백을 남긴다.
2. 시스템이 사용자 식별자와 함께 피드백 기록을 보존한다.
3. 누적된 피드백과 기존 관심사를 비교한다.
4. 충분한 근거가 확보되면 현재 선호도를 갱신한다.
5. 변경 전후 값과 변경 근거를 이력에 기록한다.
6. 요약된 장기 기억을 생성하거나 갱신한다.
7. 뉴스 요약 Agent가 기억 정보를 참고해 뉴스의 관련성을 판단한다.

초기 설계에서는 이 흐름을 정의하는 데 집중하며, 자동 갱신 로직의 구현은 별도 작업으로 남긴다.

## 5. 요약 Agent와의 연계

장기 기억은 뉴스 요약 Agent에 사용자 관심사와 선호 정보를 제공하는 역할을 한다.

예를 들어 사용자가 AI 개발 도구 관련 뉴스에 반복적으로 긍정적인 피드백을 남겼다면, 이후 뉴스 선별 시 해당 주제의 관련성을 높게 평가하는 데 참고할 수 있다.

다만 장기 기억은 뉴스의 사실 여부나 중요도를 임의로 결정하는 근거가 되어서는 안 된다. 실제 뉴스 내용과 최신성, 정보 가치를 함께 고려해야 한다.

## 6. 예외 및 관리 원칙

- 신규 사용자는 명시적으로 등록한 관심사만으로 시작한다.
- 피드백이 적으면 선호도 변경을 보류한다.
- 서로 상반된 피드백이 발생하면 단정적인 결론을 내리지 않는다.
- 관심사 변경 시 이전 이력을 유지한다.
- 사용자가 기억 삭제를 요청할 경우 관련 데이터의 삭제 범위를 고려한다.
- 개인의 민감한 정보는 뉴스 개인화에 불필요하다면 수집하거나 추론하지 않는다.

## 7. 현재 작업 범위

이번 단계에서는 장기 기억의 데이터 구조, 갱신 원칙 및 요약 Agent와의 연계 방식을 설계한다.

포함 범위:
- 사용자 선호 데이터 구조 설계
- 뉴스 피드백 데이터 구조 설계
- 선호도 변경 이력 설계
- 요약된 장기 기억 구조 설계
- 기억 갱신 흐름 정의

제외 범위:
- 실제 데이터베이스 및 테이블 구축
- 데이터베이스 연결 API 개발
- 뉴스 수집 파이프라인 연동
- 전체 서비스 자동화 및 배포

따라서 본 문서는 향후 데이터베이스 및 개인화 기능을 구현할 때 참고할 설계 기준으로 사용한다.

### 현재 구현과 설계의 차이

현재 프로토타입에서는 데이터베이스 대신 서버 메모리를 사용한다.

- 주제별 선호도 점수: -5~5
- 피드백 유형: `like`, `dislike`
- 선호도 변경 시 피드백 이력에 변경 전후 점수와 발생 시각 기록
- 사용자별 선호도와 피드백 이력을 API로 조회
- 뉴스 요약 Agent에 `topic_preferences`를 전달

설계 예시의 0~1 점수 체계와 달리 현재 구현은 긍정·부정 선호도를 모두 표현하기 위해 -5~5 점수 체계를 사용한다. 또한 현재 프로토타입은 별도의 Preference History 테이블이나 Memory Summary 자동 생성 기능을 구현하지 않았으며, 서버 재시작 시 데이터가 초기화된다.

향후 데이터베이스를 도입할 때는 현재 API의 동작을 유지하면서 영구 저장, 변경 이력 관리 및 장기 기억 요약 기능을 확장할 수 있다.
