# 사용자 테스트 결과

| 항목 | 내용 |
|---|---|
| 테스터 | 5명 (20~30대) |
| 기간 | 2026.11.7 ~ 11.8 |
| 대상 | 배포된 데모 <https://daybrief-demo.onrender.com/> |
| 방법 | 실제 사용 후 피드백 수집 → 담당 파트별 반영 |

테스터별 의견에 중복이 많아 주제별로 묶어 정리했으며, 괄호 안의 숫자는 같은 내용을 지적한 테스터 수입니다.

## 1. 긍정적인 평가

### 설정 화면

키워드를 Enter로 추가하고 "이런 키워드는 어때요?"의 추천 키워드를 바로 넣을 수 있어, 처음 쓰는 사용자도 쉽게 설정할 수 있었다는 평가를 받았습니다.

### 선정 근거 공개

브리핑 화면이 기사별 중요도 점수, 주제 태그, "왜 골랐나요", "고르지 않은 기사"와 그 사유를 함께 보여 주어 AI가 왜 이 기사를 골랐는지 확인할 수 있다는 점이 신뢰감을 준다는 의견이 있었습니다. "AI 요약에는 오류가 있을 수 있어요" 안내와 예시 화면 표시도 README의 AI 윤리 항목과 부합한다는 평가를 받았습니다.

### '내 취향' 탭 (2명)

관심사 변화를 시각적으로 보여 주어 사용자가 자신의 관심사 변화를 직관적으로 파악할 수 있다는 평가가 있었습니다. 데이터가 없을 때도 빈 화면 대신 "구독자 ID가 필요해요"라는 이유와 '관심사 설정으로 이동' 버튼을 보여 주어 다음 행동을 알 수 있다는 점도 긍정적으로 언급됐습니다.

### API 동작 확인

| 항목 | 결과 |
|---|---|
| `/health`, `/ready` | 정상 (DB 연결 포함) |
| `GET /api/news` | 실제 기사 수집 정상, 첫 요청 약 6.6초 이후 캐시로 즉시 응답 |
| `/api/news` → `/api/summarize` | 전체 흐름 정상, 요약 약 2.5초, 4건 선정 · 1건 제외 |
| 브라우저 콘솔 | 에러 없음 |

### 문서

저장소 문서가 구현된 범위와 남은 백엔드 작업(구독 관리, 인증, DB 스키마 확인 등)을 구분해 정리하고 있어, 데모 단계에서 어디까지 동작하는지 파악하기 쉬웠다는 의견이 있었습니다.

## 2. 개선 사항

### 2-1. 웹 화면과 API 서버가 연결되지 않음 (4명) — 최우선

가장 많이 지적된 문제입니다.

- 웹에서 관심 키워드를 저장해도 Network 탭의 Fetch/XHR에 요청이 나타나지 않음
- API docs에서 직접 저장하면 Supabase에 정상 기록되고 웹에도 반영됨 → 프론트엔드의 호출 로직 문제
- 키워드를 선택해도 "아직 오늘의 뉴스가 준비되지 않았어요"가 표시되고 예시 브리핑만 볼 수 있음
- 설정한 키워드('채용', '스타트업')와 무관한 'AI' 기사가 브리핑 최상단에 노출

**반영 내역**

- 키워드 추가·삭제 이벤트에서 FastAPI 저장 API를 호출하도록 연결하고, 저장된 키워드를 서버에서 다시 불러오는 기능 추가. 로컬에서 Supabase 저장과 새로고침 후 복원까지 정상 동작 확인
- "브리핑 만들기" 버튼을 `GET /api/news` → 5건씩 `POST /api/summarize` 흐름으로 연결. 키워드는 `URLSearchParams` 또는 `encodeURIComponent`로 인코딩 (한글을 그대로 보내면 서버가 요청을 거부)
- 배포/QA 담당이 재배포 후 적용

**남은 사항**: 현재 서비스에 사용자 인증이 없어 배포 환경에서는 키워드 API를 차단해 둔 상태입니다. 운영 사이트에서 Supabase 저장을 사용하려면 인증과 접근 제어를 먼저 추가해야 합니다.

### 2-2. 메일 구독을 신청할 경로가 없음 (3명)

설정 화면은 "메일 구독 때 안내받은 ID"를 입력하라고 안내하지만, 사이트에 구독 신청이나 이메일 입력 경로가 없습니다. 현재 구독자는 GitHub Secrets(`SUBSCRIBERS_JSON`)로 수동 관리하고 있어 웹 설정과 메일 브리핑이 자동으로 연결되지 않습니다.

**개선 방향**: 구글 폼(이름 · 이메일 · 키워드 · 개인정보 수집 동의)으로 신청을 받고, 사이트에 "메일로 받기" 버튼으로 연결합니다. 신청 → 등록 → 구독자 ID 안내 절차와 사용자별 데이터 접근 권한을 함께 정리해야 합니다.

### 2-3. 예시 데이터와 실제 데이터가 구분되지 않음 (3명)

- 'AI'만 선택해도 예시 브리핑에 '스타트업', '개발자 채용' 기사가 표시되고 날짜도 10월 13일로 표시됨
- 예시 화면에는 원문 링크와 피드백 버튼이 없어 좋아요 · 관심없음 기능과 그에 따른 변화를 체험할 수 없음
- 처음 방문한 사용자가 키워드 설정이 반영되지 않는다고 오해할 수 있음

**개선 방향**: 선택한 키워드에 해당하는 예시만 보여 주거나 "고정된 예시 화면"임을 분명히 표시하고, 실제 브리핑으로 전환하는 경로를 제공합니다.

### 2-4. 동음이의어 기사 혼입 (2명)

'AI' 키워드로 "고병원성 AI 확진"(조류인플루엔자) 기사가 수집됐습니다. 요약 단계에서 "AI와 무관한 H5N1 감염 사례"로 제외되어 브리핑에는 나오지 않았지만, 수집 단계에서 기사 자리를 차지합니다.

**개선 방향**: 수집 단계에 문맥 기반 필터링과 제외 규칙을 적용하되, 정상적인 기사까지 제외되지 않도록 검증이 필요합니다.

### 2-5. 진행 상태 표시와 예외 처리 (2명)

첫 수집에 몇 초가 걸리므로 "기사 모으는 중…" 같은 진행 표시가 필요합니다. 수집 · 요약 · 완료 · 오류 상태를 구분하고, 중복 실행 방지와 재시도 기능도 함께 점검해야 합니다.

### 2-6. 브리핑 결과가 저장되지 않음

서버에 브리핑 목록 · 이력 API가 없어 화면의 요약이 탭 메모리에만 유지됩니다. 새로고침하거나 탭을 닫으면 오늘의 브리핑이 사라질 수 있어, 최종본에서는 요약 결과를 서버나 DB에 저장하고 조회하는 구조가 필요합니다.

### 2-7. 피드백 저장 안정성 확인 필요

`record_feedback` 방식으로 바꿔 중복을 차단했지만, 다음 동작을 최종 QA에서 확인해야 합니다.

- 같은 기사에 좋아요를 연속으로 누를 때 점수 변화
- 좋아요에서 관심없음으로 바꿀 때 점수 변화
- 피드백 취소 · 수정 가능 여부

### 2-8. 인증 부재로 인한 보안 문제 (2명)

구독자 ID만 알면 다른 사람의 기록을 볼 수 있는 구조여서 공개 서비스의 인증으로는 쓸 수 없습니다. 정식 출시 전에 로그인 또는 세션 기반 접근 제어가 필요하며, 그전까지는 데모용이라는 점을 화면에 안내해야 합니다.

### 2-9. '준비 중' 영역이 크게 노출됨

"오늘 일정 · 중요 메일"과 "받는 시간과 채널"에 '준비 중' 표시가 크게 남아 있습니다. 캘린더 연동과 메일 선별은 이번 범위에서 제외했으므로, 숨기거나 "향후 제공 예정"으로 작게 줄이면 시연 때 덜 어색합니다.

### 2-10. '내 취향' 탭 설명 부족

"주제별 취향으로 쌓여요"라는 안내만 있어 ID를 입력하기 전에는 어떤 화면인지 알 수 없습니다. 샘플 취향 화면을 보여 주거나, 점수 범위(-5~5)와 이 점수가 다음 뉴스 선정에 어떻게 쓰이는지 한두 줄 설명이 필요합니다.

## 3. 반영 현황 요약

| 구분 | 항목 |
|---|---|
| 반영 완료 | 키워드 저장 API 연동(로컬 확인), 브리핑 생성 흐름 연결, 한글 키워드 URL 인코딩, 재배포 적용 |
| 예정 | 구독 신청 폼, 예시 데이터 구분, 동음이의어 필터, 진행 상태 표시, 브리핑 서버 저장, 피드백 동작 QA, 인증 · 접근 제어, '준비 중' 영역 정리, '내 취향' 탭 설명 보강 |

## 4. 다음 작업 순서

테스터 의견을 종합해 아래 순서로 진행합니다.

1. 웹에서 실제 데이터로 브리핑을 생성하는 전체 흐름 완성 (키워드 설정 → 서버 저장 → 수집 → 요약 → 피드백 → 취향 반영)
2. 인증 · 접근 제어 추가 후 배포 환경에서 키워드 API 차단 해제
3. 구독 신청 경로 마련
4. 뉴스 수집 정확도 및 사용성 개선
