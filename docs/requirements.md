# 요구사항 명세서 — DayBrief AI

| 항목 | 내용 |
|---|---|
| 프로젝트명 | DayBrief – AI 기반 정보 요약 자동화 |
| 팀 | 16조 (박연수, 백민서, 김의종, 김준오, 조영경) |
| 도메인 | 생산성 / AI 비서 |
| 문서 버전 | v1.0 |
| 작성일 | 2026-11-06 |

## 1. 개요

### 1.1 목적

관심 키워드를 등록한 사용자에게, 매일 아침 정해진 시간에 AI가 선별·요약한 뉴스 브리핑을 이메일로 자동 발송한다. 사용자의 피드백을 주제별 선호도로 누적해 다음 뉴스 선정에 반영함으로써, 사용할수록 개인에게 맞춰지는 브리핑을 제공한다.

### 1.2 해결하려는 문제

- 포털·뉴스레터·SNS에 흩어진 정보를 직접 선별하는 데 하루 20~30분이 소요된다.
- 출근·등교 전 짧은 시간에 관심 분야의 핵심만 파악하기 어렵다.
- 일반 뉴스레터는 모든 구독자에게 같은 내용을 보내므로 개인의 관심사를 반영하지 못한다.

### 1.3 대상 사용자

| 구분 | 설명 |
|---|---|
| 1차 대상 | 출근 전 짧은 시간에 업계 소식을 확인해야 하는 직장인 |
| 2차 대상 | 전공·취업 관련 정보를 꾸준히 확인해야 하는 학생·취업 준비생 |
| 제외 | 실시간 속보가 필요한 사용자 (일 1회 발송 구조와 맞지 않음) |

### 1.4 범위

| 포함 | 제외 |
|---|---|
| 키워드 기반 RSS 뉴스 수집 | 뉴스 원문 전체 크롤링 |
| AI 뉴스 선별·요약 | 사용자 인증·권한 관리 |
| 이메일 브리핑 자동 발송 | 공개 가입·구독 해지 기능 |
| 피드백 기반 선호도 학습 | 벡터 임베딩 기반 유사도 검색 |
| 웹 화면(브리핑 확인·피드백) | 모바일 앱 |

## 2. 사용자 시나리오

### 시나리오 1 — 가입과 설정 (D-1)

사용자가 서비스에 접속해 관심 키워드("AI", "스타트업", "개발자 이직")를 등록하고, 브리핑을 받을 시간을 아침 7시로 설정한다.

### 시나리오 2 — 브리핑 수신 (D-day 07:30)

자동화 워크플로우가 RSS에서 기사를 수집하고, AI Agent가 키워드별 주요 기사를 선별·요약해 이메일로 발송한다. 사용자는 출근길에 5분 안에 핵심 내용을 확인한다.

### 시나리오 3 — 피드백 (수신 직후)

사용자가 웹 화면에서 기사별 "좋아요 / 관심없음"을 선택한다. 선택 결과는 주제별 선호도 점수에 반영되고, 피드백 이력으로 함께 저장된다.

### 시나리오 4 — 개인화 체험 (D+7)

"AI" 주제에 좋아요가 누적되면 해당 주제 기사의 선정 우선순위가 올라가고, "스타트업"에 관심없음이 누적되면 비중이 줄어든다. 단, 선호도가 낮아도 중요도가 높은 기사는 계속 선정될 수 있다.

### 시나리오에서 도출된 개발 요소

1. 키워드 설정 화면 (Frontend)
2. 키워드 기반 뉴스 수집 (RSS Collector)
3. AI 요약·선별 Agent (Summary Agent)
4. 일일 자동 실행 (GitHub Actions)
5. 이메일 발송 (Gmail SMTP)
6. 피드백 수집·선호도 저장 (Supabase)

### 3.2 세부 규칙

**FR-02 뉴스 수집**

- 수집 피드: 연합뉴스(전체·경제·산업), 한겨레(전체·경제), 경향신문(전체), 동아일보(전체), ZDNet Korea(IT)
- 영문 키워드는 단어 경계로, 한글 키워드는 부분 일치로 매칭하며, 여러 단어 키워드는 각 단어가 모두 등장할 때 매칭한다.
- URL 추적 파라미터를 제거하고 URL·정규화 제목 기준으로 중복을 제거한다.
- 한 키워드가 결과를 독점하지 않도록 키워드별로 번갈아 선택한다.
- 피드 응답은 10분간 캐시하며, 일부 피드가 실패해도 나머지로 응답한다.

**FR-03 AI 요약**

- 중요도 배점: 관련성 40 / 정보 가치 30 / 최신성 20 / 실용성 10 (합계 0~100)
- 출력은 JSON이며 기사 ID·출처·URL·게시 시각을 원본 그대로 보존한다.
- 원문에 없는 사실·수치·발언을 생성하지 않는다.
- 선정할 기사가 없으면 빈 결과를 반환한다.

**FR-05 Long-term Memory**

- 좋아요 +1, 관심없음 -1로 점수를 조정하며 범위는 -5~5로 제한한다.
- 같은 사용자·기사·주제의 피드백은 첫 기록만 유지한다.
- 선호도는 중요도 점수에 합산하지 않고, 선정 우선순위의 보조 기준으로만 사용한다.
- 선호도가 낮다는 이유만으로 중요한 기사를 제외하지 않는다.

## 4. 비기능 요구사항

| ID | 항목 | 요구사항 |
|---|---|---|
| NFR-01 | 처리 안정성 | 요약 요청은 5건 단위로 분할하고, 실패한 묶음은 반으로 나눠 재시도한다 |
| NFR-02 | 장애 격리 | 한 구독자 처리가 실패해도 나머지 구독자 처리를 계속한다. 모든 RSS 피드가 실패하면 503을 반환하고 실패 결과는 캐시하지 않는다 |
| NFR-03 | 입력 검증 | 잘못된 요청(키워드 없음, 21개 이상, 범위를 벗어난 값 등)은 외부 호출 없이 422를 반환한다 |
| NFR-04 | 보안 | API 키·DB 서버 키는 환경 변수와 GitHub Secrets에만 저장하고 브라우저 코드·저장소에 노출하지 않는다 |
| NFR-05 | DB 접근 제어 | RLS를 활성화하고, 피드백 RPC는 서버의 service_role 권한으로만 호출한다 |
| NFR-06 | 데이터 정합성 | 선호도 갱신과 이력 저장은 하나의 트랜잭션으로 처리하고, 동시 요청은 잠금으로 직렬화한다 |
| NFR-07 | 개인정보 | 구독자 정보는 이름·이메일·키워드만 저장하고, 로그의 이메일은 마스킹한다 |
| NFR-08 | AI 윤리 | 모든 브리핑에 AI 생성물임을 표시하고 원문 링크·출처를 제공한다 |
| NFR-09 | 운영 가시성 | `/health`로 서버 생존을, `/ready`로 DB 연결을 확인한다 |
| NFR-10 | 테스트 | 외부 의존(네트워크·LLM·SMTP)을 모의 처리한 자동 테스트를 CI에서 실행한다 |
| NFR-11 | 이식성 | Python 3.10 이상(권장 3.12) 가상환경에서 동일하게 실행된다 |

## 5. 시스템 아키텍처

```
[사용자]
   │  키워드 입력 / 브리핑 확인 / 피드백
   ▼
[웹 화면 (HTML·CSS·JS)]
   │  GET /api/news · POST /api/summarize · POST /api/feedback
   ▼
[FastAPI 서버 · Render 단일 서비스]
   ├── collectors/   RSS 수집 · 키워드 필터링 · 중복 제거
   ├── agents/       Summary Agent (Groq gpt-oss-20b)
   ├── prompts/      뉴스 선별·요약 프롬프트
   └── Supabase      user_preferences · feedback_history · record_feedback

[GitHub Actions · 매일 07:30 KST]
   pipelines/daily_briefing.py → 수집 → 요약 API 호출 → Gmail SMTP 발송
```

- 화면과 API를 같은 Render 서비스에서 제공하므로 별도 프록시·CORS 설정이 필요 없다.
- 일일 발송은 Actions 내부에서 API를 실행하므로 배포 서버의 절전 상태와 무관하게 동작한다.

## 6. AI 활용 명세

| 기능 | AI 활용 방식 | 상세 설명 |
|---|---|---|
| 뉴스 선별 | AI Agent | 키워드 관련성·중복 여부·선호도를 함께 고려해 브리핑에 넣을 기사를 결정 |
| 중요도 평가 | 프롬프트 기반 평가 규칙 | 4개 항목 점수를 독립적으로 매긴 뒤 합산해 0~100점 산출, 근거가 부족하면 보수적으로 평가 |
| 기사 요약 | LLM 생성 | 기사당 2문장 이내, 첫 문장은 사건·발표, 둘째 문장은 의미·영향 |
| 개인화 | Long-term Memory | 주제별 선호도(-5~5)를 Agent 입력으로 전달해 선정 우선순위의 보조 기준으로 활용 |
| 일일 브리핑 | 자동화 워크플로우 | GitHub Actions가 수집·요약·발송을 순차 실행하고 실패 구간을 재시도 |

**모델 선택 근거**: Groq의 `openai/gpt-oss-20b`를 사용한다. OpenAI 호환 클라이언트로 호출할 수 있어 모델 교체 비용이 낮고, 무료 한도 안에서 일일 배치 처리에 충분한 응답 속도를 제공한다. 추론 토큰이 응답 한도를 소모해 JSON이 잘리는 문제가 있어 `max_completion_tokens`를 8192로 올리고 `reasoning_effort`를 낮게 설정했다.

## 7. 데이터 설계

### 7.1 user_preferences — 현재 선호

| 필드 | 설명 |
|---|---|
| user_id | 사용자 식별자 |
| topic | 주제 |
| preference_score | 선호도 점수 (-5~5) |
| updated_at | 마지막 갱신 시각 |

사용자와 주제를 기본 키로 사용한다.

### 7.2 feedback_history — 피드백 이력

| 필드 | 설명 |
|---|---|
| user_id | 사용자 식별자 |
| news_id | 대상 기사 식별자 |
| topic | 주제 |
| feedback_type | `like` 또는 `dislike` |
| previous_score / new_score | 변경 전후 점수 |
| created_at | 발생 시각 |

같은 사용자·기사·주제 조합은 첫 피드백만 기록한다.

### 7.3 뉴스 데이터 (NewsItem)

| 필드 | 설명 |
|---|---|
| id | URL의 SHA-1 해시 앞 12자리 |
| title | 기사 제목 |
| summary | RSS 본문 요약 (HTML 제거, 최대 300자) |
| source | 언론사 |
| url | 원문 URL |
| published_at | KST ISO 8601 게시 시각 |

### 7.4 구독자 목록

`data/subscribers.json`에 `user_id`, `name`, `email`, `keywords`를 저장하며 저장소에는 커밋하지 않는다. 자동 실행 시에는 GitHub Secret으로 전달한다.

## 8. 외부 인터페이스

| 메서드 | 엔드포인트 | 기능 | 주요 오류 |
|---|---|---|---|

| GET | `/health` | 서버 생존 확인 | — |

| GET | `/api/memory/{user_id}` | 선호도·피드백 이력 조회 | — |

외부 연동: 언론사 RSS 피드, Groq API, Gmail SMTP(465 실패 시 587 재시도), Supabase.

## 9. 제약사항

| 구분 | 내용 |
|---|---|
| 필수 요건 | 생성형 AI/AI Agent가 핵심 기능, 필수 기술 요소 2개 이상(본 프로젝트는 3개), 서비스 배포, 실사용자 5명 이상 피드백, GitHub 버전 관리 |
| 데이터 수집 | 네이버 검색 API는 신규 신청 중단 및 AI 요약 금지 약관으로 사용 불가 → 공개 RSS 사용 |
| 인증 | 현재 배포는 팀 시연용으로 사용자 인증·권한 분리가 없으며 가명 ID와 테스트 데이터만 사용 |
| 발송 | 개인별 발송 시간 설정 미지원, 전체 구독자 동일 시각(07:30 KST) 발송 |
| 피드백 | 메일의 GET 링크로는 피드백을 변경하지 않음 (메일 스캐너의 자동 클릭 방지) |
| 운영 | Render 무료 플랜의 절전으로 첫 요청이 지연될 수 있음, GitHub Actions 예약 실행은 정시를 보장하지 않음 |

| 대상 | 검증 방법 |
|---|---|
| Summary Agent | 정상/빈 응답/잘못된 JSON/구조 오류/키 누락 처리 테스트 |
| API | 요청 검증, 빈 뉴스 목록 처리, 선호도 전달 테스트 |
| 수집기 | 피드 시간 초과, HTML 제거, KST 변환, 키워드 매칭, 중복 제거, 균형 선택 테스트 |
| 메일 | 제목 형식, HTML 이스케이프, AI 생성 안내 문구, 텍스트 버전 테스트 |
| 파이프라인 | 분할 요청·재시도, 구독자 실패 격리, dry-run 저장 테스트 |
| 배포 | `/health`, `/ready` 확인 후 QA 문서의 외부 연동 체크리스트 수행 |

네트워크·LLM·SMTP는 모두 모의 처리하여 API 키나 인터넷 없이 실행된다. 실제 RSS 수집과 Gmail 발송은 로컬에서 별도로 확인한다.

## 11. 향후 과제

- 화면에서 `GET /api/news`를 직접 호출해 뉴스 파일 업로드 방식을 대체
- 구독 신청 폼과 개인정보 수집 동의 절차 구현
- 개인별 발송 시간 설정 및 사용자 인증
- 선호도가 실제 기사 선정 결과에 미치는 영향에 대한 비교 평가
- 언론사별로 제목이 다른 동일 사건 기사의 중복 제거 정확도 개선
- 배포 환경에서 SMTP가 막히는 경우 HTTP 기반 메일 API 전환 검토
